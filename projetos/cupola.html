01

The problem

Each UMAIN WORKS product was born on its own: with its own interface, its own login, its own action vocabulary. For people using several of them, there was no shared shell.

Every company asked the same question: which AI tool?

The result was isolated intelligence — AI that only sees the corner it was bought for.

Two names for the same thing

  1. In a first market, companies wanted a training platform.
  2. We didn’t have one product. We had four: ITS · RiskRadar · AI LMS · LevelUP.
  3. We gave it a name: Lumina Enterprise.
  4. Then universities wanted the same four. We gave it another name: Lumina Academic — exactly the same thing, with a different layout.

Giving what we sell a single name is the right call. The client needs to hear one thing, not four.

  • The same intent, written in many ways. “Generate new leads” (LeadFlow), “Generate a proposal” (QuoteGenius), “Extract data from a document” (DocuMiner), “Confirm the BOM” (BOMify), “Log a risk” (RiskRadar). The intent repeats; the button’s placement, name and behavior do not.
  • Every product repeated the same work. Identity (login, session, users and teams), settings and action bars all lived inside each product.

“Login/session, users and teams, theme” — blocks that, in the audit, became part of the Cupola shell rather than a module.

02

Finding what is shared

Together with each Product Owner, we mapped every feature of every module. Before designing a single screen, we ran an audit with all the POs to define what each module lets the user do. That shared work gave rise to the concept of action families: the same intents, named once, for every product.

  • 195 actions across 11 modules. 8 modules used the normalized format (93 actions); Vera, Voicis Core and Voicis AI were described at a different granularity, so they weigh more in the total.
  • Written and corrected by the people who know each product: 9 Product Owners involved, 13 products consulted, 12 responded (1 partially).

The 195 actions fit into 15 families

03

The Cupola concept

Not another tool. The place where tools stop being separate. One shell, many modules: the shell handles who you are, where you are and what you can do; the module handles the work.

The primary action changes with context

The Toolbar only shows the families that apply. The primary action follows what the user needs next; the vocabulary stays the same.

The agent has its own button, always to the left of the Toolbar. A free-form request is always within reach.

The decision points

We choseInstead of
Only the actions that apply — anything that doesn’t make sense leaves the Toolbar and stays in the ⌘K palette, with the reasonDisabled buttons always present, widening the bar without explaining why
View and navigate outside the Toolbar — B lives in the workspace (tabs, links, breadcrumbs)Mixing “do” and “go to” in the same bar
Module settings in the shell — one Cupola Settings page, with a section per moduleEach product with its own hidden configuration screen
04

AI in the platform

Agents do the heavy lifting. People see what they did, understand why and decide — and can always undo.

Visible

The agent works in plain sight, and the result arrives with its confidence level.

Explainable

Every answer shows where it came from: the chart, the SQL used, the sources and the reasoning.

Governed

Rules for the AI, and a log of what it decided.

How we designed the AI

VisibleExplainableReversibleGoverned
Progress on the button and the tab; reasoning steps in the conversation Confidence per row, cited sources, data freshness, explanation per profile Confirm row by row, review decisions and “Undo” after every change Autonomy and limits in Settings; policies and decisions audited in Governance
05

UMAIN WORKS design system

The brand’s own foundations and components, in Figma and in code, so every module speaks the same visual language.

  • 49 documented components (component + guidelines) · 82 public components and sets · 12 Foundations pages
  • Inside each component: visual example, anatomy, accessibility and do’s and don’ts.

How it is organized

  • Atoms — the smallest building blocks, such as a button, a tag or a text field.
  • Molecules — atoms combined into a small unit with a single job, such as a search field with its button.
  • Organisms — larger, self-contained parts of the interface, built from molecules and atoms, such as the Toolbar, a table or the Chat.

A source of truth for each team

  • Figma for designers
  • Storybook for developers (“how do I use this?”)
  • Confluence for context (“why is it like this?”)
06

Results and learnings

What this unlocks: six months later, the same company needs to find supplier datasheets and manuals. They are already in Cupola — turning on DocuMiner is a line on the invoice, not a procurement process.

What is still open

  • Defining what a “pack” is: if a pack can also be configurable content, not just code, some products start to fit.
  • Two missing families: operational commands and the “who is the action for” axis.
  • Toolbar: two versions — a single bar or the agent on its own; both are in the prototype for testing.
  • Audit still open: one product has yet to respond and one gave an incomplete answer.
  • User testing: plan and dates to be confirmed.

Next steps

  1. Design system package — modules start using the same components as the prototype.
  2. Module-by-module migration — each module adopts the shell, the families and the settings in the shell.
